# BIT101-iOS 状态与存储说明

这份文档专门说明项目里的“状态到底存在哪里”。

当你遇到下面这些问题时，应该先看这份文档：

- 为什么切号后有些状态跟着变，有些不变
- 为什么小组件拿到的数据和主 App 不完全一样
- 某个值到底在 `UserDefaults`、Keychain、文件缓存还是共享容器里
- 改动某个偏好后，为什么另一个页面没有立刻生效

## 1. 状态分类总览

当前项目里的状态大致分成七类：

1. 会话与凭据
2. 模块业务缓存
3. 界面偏好
4. 账号隔离偏好
5. 扩展共享快照
6. 页面级瞬时状态
7. 学校业务的短期认证状态

## 2. 会话与凭据

### 2.1 保存内容

这里主要包括：

- 学校统一认证账号
- 学校统一认证密码
- 与登录恢复相关的敏感凭据
- BIT101 侧会话恢复所需信息

### 2.2 保存位置

这些状态并不都在同一个存储中：

- 学号、密码：Keychain
- BIT101 `fake-cookie`、安装标记：`UserDefaults`
- 学校认证 cookie：系统 `HTTPCookieStorage`

相关代码主要在：

- `Login/LoginStorage.swift`
- `Login/LoginService.swift`

### 2.3 维护原则

- 任何敏感信息不要回落到普通 `UserDefaults`
- 如果登录链路调整了字段名或恢复逻辑，先确认旧 Keychain 迁移是否还兼容
- 卸载会清除安装标记，但 Keychain 可能由系统保留；重装后首次创建 `LoginStorage` 时会据此主动清理旧学号和密码。
- 登录态检查不能把“无法确认”当成“已失效”。网络不稳、学校页面解析失败、缺少静默恢复材料等情况应该保留本地 session 并向上抛错；只有远端明确返回凭据无效时才清除 `fake-cookie`、cookie 和本地密码。
- `fake-cookie` 为空会被外部课表快照导出为 `isLoggedIn = false`，并同步到 widget / Apple Watch。所以登录检查的清退策略会直接影响手表端是否显示“请先登录”。

### 2.4 学校业务的短期认证状态

课表、成绩、空教室和可信成绩单通过 bit-login 使用短期 challenge，包括
`challenge_id`、access token、短信状态、掩码手机号和有效期。教学中心是否已认证、已预热
也必须绑定当前学号，而不是进程级永久布尔值。

这些值只应存在于 `ScheduleService`、`ScoreService` 和对应 ViewModel 的内存中：

- 不写 Keychain 或 `UserDefaults`
- 退出、切号、过期或收到明确失效响应时立即失效
- challenge 过期或重复提交后不能继续复用
- 普通成绩的 `jwb` challenge 不能复用于可信成绩单的 `jwb_cjd`

## 3. 课表、DDL、考试与自定义日程

### 3.1 保存内容

- 课程表
- 考试
- DDL
- 自定义日程
- 一些查询所需的本地上下文

### 3.2 保存位置

当前主要是：

- 本地缓存文件

相关代码主要在：

- `Schedule/ScheduleCacheStore.swift`
- `Schedule/ScheduleModels.swift`
- `Schedule/ScheduleViewModel.swift`

### 3.3 特点

- 这类数据强调“先恢复缓存，再同步远端”
- 属于账号隔离数据
- 切号后不应继续沿用前一个账号的课表

### 3.4 覆盖更新是否会清掉本地课表

正常的 App 覆盖更新不应该清掉这一层数据。

原因是当前日程模块的主缓存不是临时内存，而是当前账号对应的本地文件缓存：

- `ScheduleCacheStore` 会把缓存写到 `Application Support/BIT101-iOS/<account>/schedule-cache.json`
- 这份缓存里不仅有主课表，也包含考试、DDL、自定义日程和导入的分享课表
- 导入别人分享的课表后，本地记录会进入 `sharedSchedules`

所以只要用户做的是：

- 直接升级新版本
- 不卸载 App
- 不手动清空本地数据

那“别人分享给我的课表”原则上也应该跟着保留。

### 3.5 分享课表为什么不会覆盖我自己的数据

分享课表的导入目标不是“同步整份日程快照”，而是“额外追加一份只读课表”。

当前导入行为是：

- 只解析课表导出载荷里的学期、首周、时间表和课程
- 把它包装成一条 `SharedScheduleRecord`
- 追加进当前账号的 `sharedSchedules`

不会一起带入，也不会覆盖：

- 我自己的主课表
- DDL
- 考试
- 自定义日程
- 课表显示偏好

所以分享课表本质上更接近“本地收藏的一份只读分身”，而不是“把我现有课表替换掉”。

### 3.6 哪些情况会真的丢数据

下面这些情况才可能导致本地数据消失：

1. 用户卸载后重装
2. 用户在设置里执行“删除所有文稿与数据”
3. 某次未来版本修改了缓存结构，但没有做好兼容解码
4. 开发时手动删除了 `Application Support` 或 `UserDefaults` 内容

其中第 3 点是维护时最需要警惕的。

当前 `ScheduleCache` 的解码策略大量使用了“缺字段就回默认值”的兼容写法，所以常见的“新增字段”通常不会破坏旧缓存；但如果未来改了字段语义、字段类型，或者直接删改了关键结构，还是要把迁移策略写清楚。

### 3.7 iCloud 课表同步

用户开启课表 iCloud 同步后，`ScheduleCloudSyncManager` 会把当前账号的完整
`ScheduleCache` 同步到 CloudKit 私有数据库：

- 记录按学号隔离
- 本地与云端按 `updatedAt` 决定应用较新版本或上传本地版本
- 关闭 `iCloudSyncEnabled` 后不再拉取或上传
- 本地文件缓存仍是 App 和扩展导出流程的直接数据来源，CloudKit 不是它们直接读取的数据库

相关代码主要在：

- `Schedule/ScheduleCloudSyncManager.swift`
- `Schedule/ScheduleCacheStore.swift`

## 4. 设置与偏好

### 4.1 保存内容

包括但不限于：

- 外观模式
- 自动旋转
- 灵动岛提前显示阈值
- 一部分查询筛选结果

### 4.2 保存位置

当前主要是：

- `UserDefaults`
- 通过 `AppSettingsStore` 做统一读写

相关代码主要在：

- `Settings/AppSettingsStore.swift`

### 4.3 两类偏好的区别

#### 4.3.1 全局偏好

例如：

- 主题模式
- 屏幕旋转

这类偏好不需要随账号变化。

#### 4.3.2 账号隔离偏好

例如：

- 一部分查询筛选
- 成绩列表缓存、学期/种类筛选与排序偏好
- 普通帖子页面是否隐藏机器人帖子（搜索、推荐、关注、个人主页等；机器人分栏除外）

这类偏好必须按账号分桶。

可信成绩单不属于业务缓存。图片由学校生成的短期 URL 下载，使用 ephemeral URLSession，
只在申请页 ViewModel 中持有 `UIImage`；退出页面后不应进入 `CachedRemoteImage` 的磁盘缓存。

### 4.4 实验性偏好 iCloud 同步

用户单独开启实验开关后，`ExperimentalPreferenceCloudSync` 使用 iCloud Key-Value Store
同步设置、成绩筛选、成绩缓存和话廊消息已读状态：

- 开关保存在当前设备并按学号隔离，默认关闭
- 各同步域分别记录修改时间，避免一个域覆盖另一个域
- 它不负责课表；课表使用上一节所述的 CloudKit 同步

相关代码主要在：

- `Shared/Infrastructure/ExperimentalPreferenceCloudSync.swift`
- `Score/ScoreCacheStore.swift`

## 5. 话廊的本地状态

### 5.1 服务端状态

服务端提供：

- 帖子列表
- 评论
- 分类未读数

### 5.2 本地派生状态

客户端额外维护：

- 当前 feed 的分页状态
- 搜索状态
- 消息页“伪新消息”

这里最容易混淆的是“消息已读”。

当前项目并没有真正的服务端逐条已读状态，而是：

- 服务端给分类未读数
- 客户端基于这份计数做本地近似展示

所以它的本质是：

- UI 体验状态
- 不是严格一致的消息存档状态

## 6. 小组件与锁屏组件的数据来源

### 6.1 为什么不能直接读主 App 缓存

因为：

- 主 App 缓存结构更复杂
- 扩展 target 不应该深耦合业务内部对象
- 共享边界太宽会让维护成本明显上升

### 6.2 当前做法

当前设计是：

1. 主 App 维护完整课表缓存
2. `ScheduleWidgetSupport.swift` 导出精简快照
3. widget / 锁屏组件 / Live Activity 只读取共享快照

### 6.3 保存位置

共享快照保存在：

- App Group 共享容器

标识为：

- `group.BIT101-dev.BIT101-iOS.shared`

## 7. Live Activity 的额外运行时状态

Live Activity 不是“存一份静态数据就结束”，它还依赖运行时判断：

- 当前是否有课
- 下一节课还有多久
- 当前是否命中提前显示阈值
- 当前账号有没有开启该功能

所以它使用的是：

- 共享快照
- 当前时间
- 本地设置
- 当前运行中的 activity 状态

这也意味着：它的显示结果是动态计算的，不是单纯读一份数据库。

## 8. 头像缓存

### 8.1 当前状态

头像不再只依赖系统默认网络缓存，而是有显式缓存层。

### 8.2 目的

- 避免冷启动时重复下载头像
- 减少列表滚动中的图片抖动
- 提高“我的”“话廊”“消息中心”的稳定性

### 8.3 保存位置

这部分同时依赖：

- 内存缓存
- 磁盘缓存

相关代码在：

- `CachedRemoteImage.swift`

## 9. 页面瞬时状态

不是所有状态都应该落盘。

例如：

- sheet 是否打开
- 当前搜索输入
- 当前正在加载更多
- 当前帖子详情是否展开
- bit-login 短信 challenge 和验证码错误
- 可信成绩单临时图片与全屏预览状态

这类状态通常应停留在：

- `@State`
- `@StateObject`
- `ViewModel` 的内存属性

不要为了“怕丢”就把瞬时状态写进持久化层，否则只会让行为越来越难解释。

## 10. 判断某个新状态该放哪

如果你准备新增一个状态，建议先按下面顺序判断：

1. 它是不是敏感信息
   - 是：优先 Keychain
2. 它是不是跨启动仍要恢复的业务数据
   - 是：缓存文件或 `UserDefaults`
3. 它是不是应该按账号隔离
   - 是：不要存成全局唯一值
4. 它是不是扩展要读
   - 是：导出精简快照，不要直接共享主缓存
5. 它是不是只影响当前页面一小段时间
   - 是：留在内存，不要落盘

这套判断比“看到哪里方便就往哪里存”更重要。
